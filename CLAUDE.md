# CLAUDE.md

Руководство для Claude Code по этому каталогу. Читается перед любой работой.

## Что за проект

«Арена переговоров» — симулятор переговоров для ОЭЗ «Алабуга» (хакатон LCT 2026). Продукт
состоит из двух приложений.

**Клиент-тренажёр** — приложение, в котором сотрудник ведёт переговоры голосом с ИИ-оппонентом.
Его пишет другая команда, и на момент этой работы его ещё нет. Там живёт весь цикл хода:
распознавание речи, вызовы трёх моделей (оппонент, судья участника, судья оппонента),
пересчёт шкал, переходы между этапами, синтез голоса, обе оценки.

**Портал HR** — веб-система, в которой методолог создаёт сценарии, HR выдаёт доступ и читает
результаты, администратор ведёт настройки. **Мы пишем бэкенд портала** — один процесс на Go,
модульный монолит поверх PostgreSQL 16, девятнадцать модулей и платформенный слой. Он
обслуживает двух потребителей: `/api/portal/*` (веб-портал HR, вход по cookie)
и `/api/trainer/*` (клиент-тренажёр, вход по токену).

## Действующие решения

Эти решения отменяют написанное в спецификациях. Там, где документ говорит иначе, — прав
этот список.

| Решение | Что было в документах |
|---|---|
| Бэкенд — **Go**, `chi`, `pgx/v5` | `arena-api.md` 1, `arena-db.md`: «один процесс на Node.js» |
| Пакет движка `@arena/engine` **не используется вовсе** | `arena-api.md` 1, `arena-scenario-format.md` 19 |
| Доступ к базе — **чистый SQL**, без ORM и без кодогенерации | — |

| Документ сценария уходит клиенту **целиком**, на публичную и приватную половины не делится | `arena-scenario-format.md` 16, FR-AC-04 |

### Авторство сценария

Методолог описывает сценарий голосом; запись собирается в mp3 и уходит на бэкенд. Портал
расшифровывает её и отдаёт модели, которая возвращает документ сценария (JSON) со всеми
составляющими — условиями переходов, пределами сделки, скрытыми фактами. Документ уходит
на фронтенд портала и показывается интерактивной формой.

Шесть равноправных способов: создать голосом · править голосом · прислать описание текстом ·
править текстом · создать через форму · править через форму. Подробности —
`arena-portal-hr.md` 11.6 и `arena-portal-backend-architecture.md` 10.2.

**mp3 нигде не хранится** — ни в базе, ни на диске, ни в логе. Сохраняется только расшифровка,
в `scenarios.generation`. В `audit_log.details` она не попадает.

Модели настраиваются переменными окружения (`ARENA_STT_*`, `ARENA_GEN_*`) и **необязательны**:
без них портал поднимается, адреса генерации отвечают 503 с русским текстом, а форма, шаблоны,
копия и импорт работают как обычно. В цикле разговора портал моделей по-прежнему не вызывает.

## Правила, которые нельзя нарушать

На каждом из них держится требование, и каждое проверяется тестом.

1. **Ключ `emotion`** на любой глубине тела — 400, **до записи тела куда-либо**, включая лог.
   Совпадение имени точное: профиль с полем `camera.emotion_labels_to_opponent` должен
   сохраняться (FR-RS-02).
2. **Две оценки нигде не складываются** — ни поля, ни переменной с суммой или средним
   «результата» и «процесса» (FR-RS-04).
3. **Нет доступа к группе — 403, а не пустой список** (FR-AC-08). Роль и доступ читаются
   из базы на каждом запросе, а не берутся из cookie или токена. Доступ к сессии проверяется
   по группе назначения (`sessions.group_id`), а не по текущей группе сотрудника.
4. **Запись в журнал — в той же транзакции, что и действие.** Отказ в доступе тоже пишется,
   с `outcome = 'denied'` (NFR-S-03).
5. **Имён и текстов реплик в журнал и в лог не пишем** — ни в `details`, ни в сообщениях.
6. **`NOT is_demo` в каждом запросе аналитики**: иначе демо-сессии попадут в статистику
   (FR-AC-10), а индексы, построенные с этим условием, не сработают.
7. **`arena-db.sql` приложение не меняет.** Схему создаёт роль-владелец; дальнейшие изменения —
   нумерованные файлы поверх, только вперёд. У роли `arena_app` нет прав на DDL, нет `DELETE`
   на журнале и нет `UPDATE` на опубликованных версиях — это защита, а не неудобство.
8. **Никаких молчаливых отказов** (NFR-R-03): у каждой ветки обработки ошибки есть видимое
   состояние и готовая русская фраза. Пустой `catch` — дефект.
9. **Ключи провайдеров наружу не отдаются** никому в портале, даже администратору: видны
   только последние 4 знака. Целиком ключ получает клиент-тренажёр, и только при старте сессии
   и при погашении ссылки на репетицию.

## Устройство модуля

```
internal/modules/<модуль>/
  contract.go     интерфейсы и DTO — только это видят другие модули
  module.go       сборка: зависимости на входе, маршруты на выходе
  transport.go    HTTP: разбор, проверка тела по схеме, вызов службы, ответ
  service.go      сценарии использования: правила, транзакции, журнал
  store.go        SQL: единственное место, где модуль ходит в свои таблицы
```

- `transport` не знает SQL и не открывает транзакций.
- `service` не знает HTTP: ни кодов состояния, ни заголовков. Одна транзакция на один сценарий
  использования, вместе с записью в журнал.
- `store` не знает правил: превращает ошибки PostgreSQL в доменные.
- **К чужим таблицам не ходим даже на чтение**: `analytics` читает сессии через контракт
  `sessions`, а не своим `SELECT`. Границы держит линтер импортов — обязательная часть сборки.
- Зависимости собираются явно в `cmd/portal/main.go`, без контейнера зависимостей.
- Исключение — `scenariodoc`: чистые функции над документом сценария, без HTTP и без базы.

## Команды

Документация проверяется из `hack_alab`:

```bash
python3 -c "import yaml; yaml.safe_load(open('arena-api.yaml'))"   # контракт разбирается
```

Код — из `project/` (`Makefile`; нужен файл `.env`, см. `.env.example`):

```bash
make up               # docker compose: постgres + портал, разворачивание — клон и одна команда
make down              # остановить
make test              # go test ./...
make test-integration  # интеграционные тесты — нужен поднятый postgres (make up)
make lint               # линтер границ модулей (depguard)
make gen                # go generate ./... — перегенерировать HTTP-типы из контракта
make tidy                # go mod tidy
```

**`project/README.md` правим в том же заходе, что и всё, что меняет запуск** — `Makefile`,
`deploy/` (Dockerfile, docker-compose.yml, init-скрипты), `.env.example`, набор обязательных
переменных окружения, структуру каталогов. Не отдельным поручением и не потом: README не
должен разойтись с тем, что реально нужно для `make up`.

## Язык

Весь пользовательский текст — по-русски: `title` в `problem+json` показывается на экране как
есть, сообщения проверки сценария говорят на языке предмета («Сергей никогда не обидится —
вы не описали, что его задевает»), а не служебными идентификаторами (FR-SC-07). Спецификации
и общение с пользователем — тоже по-русски.

## Чего не предлагать

- Node.js или TypeScript для портала; интеграцию с пакетом движка.
- ORM, `sqlc` и прочую кодогенерацию слоя запросов.
- Пересчёт оценок на портале и сверку своего расчёта с клиентским.
- Любые поля под лицо, голос участника и метки эмоций — их нет ни в API, ни в базе, ни в логах.
- Правку `arena-db.sql` на месте.
- Возврат анкеты из десяти полей и трёхшаговой генерации с подтверждением — они отменены.

## Известные расхождения, которые мы не правим

Чтобы не «чинить» их в следующий раз. **Править эти файлы без отдельной просьбы не нужно** —
достаточно знать, где они расходятся.

- **`arena-api.yaml` отстаёт от требований.** Контракт описывает 82 адреса и старый путь
  создания сценария: анкету `Questionnaire` из десяти полей и адреса
  `/generation/steps/{step}/confirm` и `/generation/steps/{step}/regenerate`. Актуальны
  `arena-portal-hr.md` 8 и 11.6 и `arena-portal-backend-architecture.md` 10.2, где адресов 84:
  вместо двух шаговых — `generation/audio`, `generation/text`, `draft/voice-edit`,
  `draft/text-edit`. Там же FR-SC-11 помечено снятым, а в контракте он ещё в `x-fr`.
- Комментарий `scenarios.draft_fingerprint` в `arena-db.sql` говорит «считает пакет движка».
  Отпечаток считает портал; `arena-db.sql` трогать нельзя, так что расхождение остаётся.
- `arena-api.md` раздел 1 и `arena-db.md` написаны в расчёте на Node.js и пакет движка.
- `arena-scenario-format.md` раздел 19 отдаёт формат сценария движку и описывает
  `authoring.questionnaire` — анкету из десяти полей. Анкеты больше нет: поле называется
  `authoring.brief` и хранит описание, с которого начался сценарий (расшифровку надиктованного
  или присланный текст). Прав `arena-portal-hr.md` 11.1.
- Файлы `arena-scenario.schema.json`, `arena-consent-texts.md` и `arena-scenario-example.json`,
  на которые ссылаются документы, не существуют и не восстанавливаются.
