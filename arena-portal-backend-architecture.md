## 1. Назначение и границы

Бэкенд портала — **один процесс на Go**, модульный монолит поверх PostgreSQL 16. Он обслуживает
два потребителя: веб-портал HR (`/api/portal/*`, вход по cookie) и клиент-тренажёр
(`/api/trainer/*`, вход по токену). Оба обращаются к одному процессу.

### Что он делает

| Область | Суть |
|---|---|
| Сценарии | хранит документы, проверяет их по пятнадцати правилам, публикует неизменяемые версии, ведёт библиотеку, импорт и экспорт |
| Авторство | принимает описание сценария голосом (mp3) или текстом, расшифровывает речь, получает у модели документ сценария и правит готовый черновик по голосовому или текстовому указанию |
| Выдача клиенту | по коду доступа отдаёт документ сценария, уровень сложности, профиль тренажёра и ключи моделей — одинаково для сессии и для репетиции |
| Назначения | назначения, коды доступа, сроки, блокировки, перевыпуск |
| Приём разговора | принимает пачки событий хода, ведёт лог реплик, считает пометки, принимает завершение с готовыми оценками |
| Результаты | отдаёт обе оценки с раскрытием любого числа до цитаты, запись сессии, динамику, сравнение, аналитику, выгрузки |
| Люди и доступ | сотрудники, группы, роли, доступ к группам, согласия, отзыв согласия |
| Право | кадровые решения, возражения, журнал действий, шифрование, обезличивание |

### Чего он не делает

- **Не ведёт разговор.** Цикл хода целиком в клиенте: распознавание речи, вызовы оппонента
  и двух судей, пересчёт шкал, переходы между этапами, синтез голоса.
- **Не вызывает модели разговора.** Ни оппонента, ни двух судей, ни для пересчёта оценок.
  К моделям портал обращается только ради авторства сценария: распознавание речи и генерация
  документа (раздел 10.2). Третье такое место — «Проверить профиль», и оно пока заглушка.
- **Не считает оценки.** Обе приходят с клиента готовыми (раздел 8).
- **Не делит документ сценария** на публичную и приватную половины — отдаёт целиком (раздел 12).
- **Не обрабатывает лицо, голос и эмоции.** Полей для них нет ни в API, ни в базе, и запрос
  с ключом `emotion` отклоняется.

### Нагрузка

Пилот: сотни сессий, десятки тысяч ходов, одна копия портала. Отдельное хранилище аналитики
не нужно — все экраны строятся из `sessions` и `turns` по индексам, уже заложенным в схему.
Счётчики частоты запросов живут в памяти процесса; когда копий станет больше одной, они
переезжают в базу или Redis.

## 2. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **Go** | решение команды |
| HTTP | **chi** | тонкий роутер поверх `net/http`, группы маршрутов и middleware ложатся на разделение `/api/portal` и `/api/trainer`, никакой магии |
| База | **PostgreSQL 16** | требование схемы: `gen_random_uuid()` в ядре, вычисляемые столбцы, jsonb, частичные индексы |
| Драйвер | **pgx/v5** | нативный протокол, поддержка jsonb, массивов, `timestamptz` и перечислений без обёрток |
| Доступ к данным | **чистый SQL** | схема написана руками и опирается на вещи, которые ORM не выражает; запросы аналитики из `arena-db.md` (раздел 7) переносятся в код как есть |
| Миграции | **`arena-db.sql` как есть** + нумерованные файлы поверх | DDL остаётся единственным источником правды о схеме |
| Пароли | **argon2id** | указано в схеме (`portal_users.password_hash`) |
| Шифрование | **AES-256-GCM**, HMAC-SHA256 | указано в `arena-db.md` разделе 5 |
| Проверка тел | **JSON Schema из `arena-api.yaml`** | схемы уже закрыты (`additionalProperties: false`); писать вторую проверку руками — плодить расхождения |
| Выгрузки | `encoding/csv` + библиотека XLSX | FR-ST-07 |
| Модели авторства | **HTTP-клиент на `net/http`** к совместимому с OpenAI адресу: расшифровка речи и структурированный ответ по схеме документа | нужны ровно два вызова (раздел 10.2); отдельный SDK ради них добавил бы зависимость и ничего не упростил |
| Развёртывание | **Docker Compose**: портал + Postgres | NFR-D-01: клон и одна команда |

### Почему не ORM

`arena-db.sql` опирается на вычисляемые столбцы (`consent_records.usable`,
`rehearsals.counts_for_admission`), составные внешние ключи на три столбца (три ссылки сессии
на согласия, `hr_decision_sessions`), отложенные триггеры (`hr_decisions_need_session`),
частичные уникальные индексы (одна идущая сессия на назначение, один действующий код,
один профиль по умолчанию), представление `trainer_profiles_public` и права роли `arena_app`,
выданные по отдельным столбцам. ORM всё это не выражает и всё равно уходит в сырые запросы,
но при этом заводит вторую модель схемы, которая расходится с первой.

### Открытое решение: генерация кода из контракта

В `arena-api.yaml` уже описаны 84 адреса и около 150 схем. Есть три пути:

1. **Генерировать типы и сигнатуры обработчиков** (`oapi-codegen`). Контракт остаётся
   единственным источником правды, типы физически не могут разойтись со спецификацией,
   несоответствие ловит компилятор. Расплата — шаг генерации в сборке и форма кода,
   продиктованная генератором.
2. **Генерировать только типы**, маршруты и middleware писать руками. Середина.
3. **Писать всё руками**, YAML оставить документацией. Больше свободы, но 150 структур придётся
   держать в согласии с контрактом ручной дисциплиной.

**Рекомендация — вариант 1 или 2.** Решение обратимое: сгенерированные типы всегда можно
зафиксировать в репозитории и перестать генерировать. Независимо от выбора, **проверка тел
запросов выполняется по схемам из того же YAML** отдельным middleware — иначе закрытые схемы
(`additionalProperties: false`) не работают, а на них держится FR-RS-02.

Девятнадцать модулей и платформенный слой. Модуль — это область ответственности с собственными
таблицами и собственным публичным контрактом; обращение к чужим таблицам напрямую запрещено.

```

internal/
  modules/
    auth/         people/        consents/     profiles/
    scenarios/    scenariodoc/   generation/   rehearsals/
    assignments/  sessions/      results/      analytics/
    exports/      decisions/     objections/   audit/
    settings/     demo/          jobs/
  platform/
    config/  pg/  crypto/  ai/  httpx/  ratelimit/  log/

db/seed/                     демо-данные (NFR-D-04)
deploy/                      Dockerfile, docker-compose.yml, .env.example
```

### 3.3. Зависимости между модулями

Разрешены только через публичные контракты. Основные направления:

```
sessions    → assignments (найти назначение и код), consents (проверить ответы),
              profiles (снимок настроек и ключи), scenarios (документ версии),
              people (ключ данных участника), audit
results     → sessions (чтение), people, audit
analytics   → sessions (чтение), scenarios (документ версии), audit
exports     → sessions, people, scenarios, audit
decisions   → sessions (пригодность), people, audit
objections  → sessions, people, audit
scenarios   → scenariodoc (проверка, отпечаток, шаблоны, уровни), rehearsals (счётчик допуска), audit
rehearsals  → scenarios (черновик и отпечаток), profiles (ключи), audit
generation  → platform/ai (расшифровка и генерация), scenariodoc (проверка документа),
              scenarios (чтение и сохранение черновика), audit
assignments → people, profiles, scenarios (версия), audit
demo        → sessions, consents, profiles
jobs        → sessions, scenarios, audit
auth        → people (доступ к группам)
```

`scenariodoc`, `audit`, `platform/*` не зависят ни от кого. Циклов нет: если два модуля тянутся
друг к другу, зависимость разворачивается интерфейсом на стороне потребителя.

## 4. Устройство модуля

Внутри модуля три слоя и один файл контракта.

```
internal/modules/scenarios/
  contract.go     что модуль обещает наружу: интерфейсы и DTO. Только это видят другие модули
  module.go       сборка: зависимости на входе, регистрация маршрутов на выходе
  transport.go    HTTP: разбор запроса, проверка тела по схеме, вызов службы, ответ
  service.go      сценарии использования: правила, транзакции, запись в журнал
  store.go        SQL: единственное место, где модуль ходит в свои таблицы
  queries/*.sql   тексты запросов, если их много и они длинные
  service_test.go
```

**Правила слоёв.**

- `transport` не знает SQL и не открывает транзакций. Его работа — разобрать запрос,
  проверить тело, достать из контекста, кто вызывает, и превратить доменную ошибку в ответ
  `problem+json`.
- `service` не знает HTTP: ни кодов состояния, ни заголовков. Он владеет транзакцией — одна
  транзакция на один сценарий использования, вместе с записью в журнал.
- `store` не знает правил: он выполняет запросы и превращает ошибки PostgreSQL в доменные
  (нарушение уникального индекса «одна идущая сессия» — это не «ошибка базы», а «сессия
  уже идёт»).
- Обращаться к чужим таблицам напрямую нельзя даже на чтение: `analytics` читает сессии
  через контракт `sessions`, а не своим `SELECT` по `arena.sessions`.

**Сборка.** Никакого контейнера зависимостей: в `cmd/portal/main.go` модули создаются явно,
в порядке зависимостей, и получают друг друга через интерфейсы из `contract.go`. Так видно,
кто от кого зависит, и цикл не собирается.

**Границы держит линтер импортов** (`depguard` или `go-arch-lint`): импорт
`internal/modules/<чужой>/store` или `…/service` из другого модуля запрещён, разрешён только
`…/<чужой>` (корень пакета с контрактом). Это обязательная часть сборки: без линтера модульный
монолит за месяц превращается в обычный.

**Исключение — `scenariodoc`.** У него нет ни транспорта, ни хранилища: это чистые функции над
документом сценария. Он не зависит ни от базы, ни от HTTP, и тестируется без них.

## 5. Сквозные правила

Эти правила действуют во всех модулях. Каждое — реализация конкретного требования, и каждое
проверяется тестом.

### 5.1. Доступ

1. **Роль и доступ к группам читаются из базы на каждом запросе**, а не берутся из cookie:
   снятый доступ действует немедленно (FR-AC-08, UC-A-06).
2. **Доступ к сессии проверяется по группе назначения** (`sessions.group_id`), а не по текущей
   группе сотрудника. Условие подмешивается в каждый запрос к результатам:
   `AND s.group_id IN (SELECT group_id FROM arena.user_group_access WHERE user_id = $me)`.
3. **Нет доступа — 403, а не пустой список** (FR-AC-08). Это касается и фильтра по чужой группе.
4. Результаты **любой** роли, включая администратора, открываются только по доступу к группе.
5. Урезанный вид (FR-ST-02) — отдельная проекция, а не тот же ответ с вырезанными полями:
   имени и текста реплик в нём нет физически.

### 5.2. Журнал

6. Каждое действие из списка NFR-S-03 добавляет строку `audit_log` **в той же транзакции**,
   что и само действие. Отказ в доступе тоже пишется, с `outcome = 'denied'`.
7. **Имён и текстов реплик в журнал не пишем** — ни в `details`, ни в сообщениях лога.
   Это правило кода, база его не держит; проверяется ревью и тестом на `details`.
8. Выгрузка по нескольким группам пишет **по строке на каждую группу** со своим `group_id`
   и `rows_count` и общим идентификатором выгрузки в `details` (FR-RS-10).

### 5.3. Оценки

9. **Нигде нет поля с суммой или средним двух оценок** (FR-RS-04). Проверяется поиском по коду
   и по схемам ответа.
10. Буква финала возвращается только вместе с названием финала и эпилогом; база это же держит
    ограничением.
11. Сравнение и сортировка — только внутри одного набора условий: режим, версия сценария,
    уровень сложности, набор критериев, профиль оценки (FR-ST-05). При неполных условиях ответ
    200 со списком доступных сочетаний, а не ошибка.
12. Доли, средние и сравнения по выборке меньше тридцати сессий несут пометку «мало данных»
    с числом сессий (FR-ST-09). Пометку ставит бэкенд, а не клиент: иначе она потеряется
    в выгрузке.

### 5.4. Тела запросов

13. Тела клиента-тренажёра проверяются по **закрытым** схемам из контракта
    (`additionalProperties: false`). Лишнее поле — 400.
14. Тело, в котором на любой глубине встречается ключ с именем **ровно** `emotion`, отклоняется
    с 400 **до записи тела куда-либо** — в том числе до записи в лог (FR-RS-02). Именно точное
    совпадение имени, а не подстрока: иначе не сохранится профиль с полем
    `camera.emotion_labels_to_opponent`.
15. Ограничение размера: 1 МБ на тело, 5 МБ на запись репетиции, 25 МБ на mp3 с описанием
    сценария, не больше 100 событий в пачке.
16. **Два адреса авторства голосом — единственные, где тело не JSON.** Они принимают
    `multipart/form-data` с одним файлом; проверка по закрытой схеме и правило про ключ
    `emotion` к ним неприменимы и остаются на всех остальных адресах. Расшифровка mp3
    не пишется ни в лог, ни в `audit_log.details`, а сам файл не сохраняется (раздел 10.2).

### 5.5. Прочее

17. **Снимок профиля пишется в сессию при старте** (`profile_snapshot`, `profile_revision`);
    идущая сессия профиль больше не читает (FR-PF-03).
18. **Никаких молчаливых отказов** (NFR-R-03): у каждой ветки обработки ошибки есть видимое
    состояние и текст по-русски. Пустой `catch` — дефект.
19. Ограничения частоты — четыре предела из контракта, счётчики в памяти процесса.
20. Все тексты ошибок для экрана — по-русски и готовыми фразами: `title` в `problem+json`
    показывается пользователю как есть.

## 6. Работа с базой

### 6.1. Схема — не наша

`arena-db.sql` выполняется на пустой базе одной командой и создаёт схему `arena`, роль
`arena_app`, 14 перечислений, 20 таблиц, представление, индексы, два триггера и права.
**Приложение не может менять структуру таблиц.** Порядок развёртывания:

```
1. роль-владелец выполняет db/schema/arena-db.sql
2. роль-владелец выполняет db/schema/NNN_*.sql — последующие изменения, по одному файлу
3. приложение подключается под ролью arena_app и при пустой базе заливает демо-данные
```

Миграции нумерованные и только вперёд. Ни одна из них не выполняется приложением под
`arena_app`: у этой роли нет прав на DDL, и это защита, а не неудобство.

### 6.2. Права роли ограничивают приложение намеренно

| Таблица | Что можно `arena_app` | Зачем |
|---|---|---|
| `audit_log` | `SELECT`, `INSERT` | журнал только дополняется (NFR-S-03) |
| `scenario_versions` | `SELECT`, `INSERT` | версии неизменяемы (FR-SC-09) |
| `hr_decisions`, `hr_decision_sessions` | `SELECT`, `INSERT` | решения не правятся (FR-RS-08) |
| `rehearsals` | `SELECT`, `INSERT`, `UPDATE` только столбцов погашения и записи | отпечаток, уровень, профиль и получателя поменять нельзя |
| `trainer_profiles` | `SELECT`, `INSERT`, `UPDATE` всех столбцов **кроме** `id`, `is_default`, `created_at` | профиль по умолчанию нельзя снять (FR-PF-05) |
| `objections` | `SELECT`, `INSERT`, `UPDATE` только трёх столбцов ответа | возражение не переписывается |
| `people`, `user_group_access` | плюс `DELETE` | это единственные две таблицы, где удаление нужно (NFR-PR-01, UC-A-06) |

Следствие для кода: попытка «просто поправить» такую строку падает не на ревью, а в рантайме
и в тестах. Если запрос требует прав, которых нет, это сигнал, что нарушается требование.

### 6.3. Транзакции

Одна транзакция на один сценарий использования, вместе с записью в журнал. Отдельно стоит
отметить три места:

**Выпуск кодов.** Селектор уникален среди действующих кодов, а в нём всего 20 бит: при тысяче
действующих кодов пачка на 500 человек примерно в половине случаев встретит совпадение. Поэтому
массовое назначение и перевыпуск вставляют **каждый код через точку сохранения** и при ошибке
уникальности на этом индексе выпускают код заново, до пяти попыток. Пачка целиком не откатывается.

**Перевыпуск кода.** Одна транзакция: у старой строки `revoked_at`, новая строка. Частичный
уникальный индекс не даст вставить второй действующий код, не отозвав первый, — значит, старый
код перестаёт работать немедленно (FR-AC-12).

**Отзыв согласия.** Одна транзакция из пяти шагов (раздел 9.3).

### 6.4. Запросы аналитики

Готовые запросы для всех экранов раздела статистики уже написаны в `arena-db.md`, раздел 7,
и переносятся в код как есть: распределение по финалам, найденные скрытые факты
(`CROSS JOIN LATERAL unnest`), слабые места группы (`CROSS JOIN LATERAL jsonb_each_text`
по `criteria_bands`), сравнение сотрудников (оконные функции `count` и `row_number`),
закрытие брошенных сессий. Индексы под них в схеме уже есть; все индексы аналитики построены
с условием `NOT is_demo`, и это же условие обязано стоять в каждом запросе — иначе демо-сессии
попадут в статистику (FR-AC-10), а индекс не сработает.

### 6.5. Работа с jsonb

Портал не заглядывает внутрь чужих объектов и хранит их как есть: документ сценария, настройки
профиля, решения судей, пошаговый разбор хода, блок оценок, ответ судьи после разговора, запись
репетиции. Исключения, где портал читает jsonb, — их немного и они перечислены:

- `scenarios.draft_document->'passport'` — название, сфера, тип и теги для библиотеки;
- `scenarios.generation` — состояние задания авторства: этап, расшифровка, число повторов,
  ошибка; у ещё не сгенерированного сценария из неё же берётся название для библиотеки;
- `sessions.criteria_bands` — полосы критериев для аналитики группы и динамики;
- весь документ сценария внутри модуля `scenariodoc` — это его работа.

## 7. Приём событий хода

Самый нагруженный путь и единственный, где важна договорённость с чужой командой.

### 7.1. Договорённость с клиентом

- **Каждая реплика отправляется одним событием, уже с решением своего судьи**: у участника —
  с решением судьи участника, у оппонента — с решением судьи оппонента или с пометкой
  «судья не ответил». Лог только дополняется, поэтому дописать решение потом нельзя.
- Пачка — до 100 событий; событие несёт `seq`, и ключ `(session_id, seq)` **отбрасывает дубли
  сам**. Отдельного заголовка идемпотентности нет и не нужно.
- Заполнители («Так…», «Секунду…») в лог не пишутся.
- Отказы компонентов (камера, распознавание, синтез, смена адреса моделей) приходят
  в том же потоке со своим идентификатором события и складываются в `sessions.incidents`.

### 7.2. Что делает портал на пачке

```
1. проверить тело по закрытой схеме, отклонить ключ emotion
2. в одной транзакции:
   2.1 вставить строки turns (дубли отбрасывает первичный ключ)
   2.2 зашифровать тексты ключом участника; ключ уничтожен → text_enc = NULL
   2.3 вырезать comment из решения судьи оппонента в отдельный шифрованный столбец
   2.4 обновить sessions: last_event_at, participant_turns,
       opponent_violation_count, simplified, stub_used, incidents
   2.5 если simplified стал истинным — снять отметку «просмотрено» тем же UPDATE
   2.6 если сессия была abandoned — вернуть in_progress, очистить ended_at,
       process_status = pending, reopened_count + 1, запись session_reopened в журнал
3. ответить, что принято и открылась ли сессия заново
```

**Если по тому же назначению уже идёт другая сессия**, частичный уникальный индекс не даст
вернуть статус: ходы дописываются, статус остаётся `abandoned`, в ответе `reopened = false`
и пояснение.

**Пока сессия идёт или прервана, отметку «просмотрено» поставить нельзя** (409): поздние ходы
ещё могут добавить нарушения оппонента.

### 7.3. Закрытие брошенных сессий

Задание модуля `jobs` раз в минуту:

```sql
UPDATE arena.sessions s
   SET status = 'abandoned', ended_at = now(), process_status = 'not_scored',
       break_turn = s.participant_turns,
       break_stage = (SELECT t.stage FROM arena.turns t
                      WHERE t.session_id = s.id ORDER BY t.seq DESC LIMIT 1)
 WHERE s.status = 'in_progress'
   AND greatest(s.last_event_at, $portal_started_at) < now() - make_interval(mins => $timeout)
RETURNING s.id;
```

По каждому возвращённому идентификатору — запись `session_closed_by_server` в журнал.
`$portal_started_at` — время запуска процесса: **время недоступности портала в таймаут
не входит** (FR-ST-03). Это значит, что портал обязан помнить момент своего старта; при
нескольких копиях это правило придётся переписывать.

### 7.4. Поведение при недоступности портала

Со стороны портала делать нечего — буфер держит клиент, — но приёмка требования FR-AC-11
проверяет именно бэкенд: после восстановления в базе должны появиться **все** ходы, включая
пришедшие с опозданием, и сессия должна корректно перейти в итоговый статус по позднему
завершению.

## 8. Оценки от клиента

### 8.1. Что приходит

В запросе завершения сессии клиент присылает итоговый статус, причину остановки и блок оценок:
обе оценки, финал и букву, максимум сценария, полосы по шести критериям, эпизоды засчитанные
и отброшенные с причиной, сработавшие потолки, профиль оценки, отметку «повезло», число запросов
к судье и ответ судьи после разговора с цитатами и резюме.

### 8.2. Что проверяет портал

Только форму. Логику оценивания портал не повторяет.

| Проверка | Почему |
|---|---|
| числа оценок целые в диапазоне 0–100 | столбцы `smallint`, экраны считают проценты |
| буква из перечисления `final_rank` и **только вместе с финалом** | FR-RS-04, ограничение базы `sessions_rank_with_final` |
| полосы критериев — целые 0–4, ключи из шести известных критериев | из них считается аналитика группы |
| набор критериев совпадает с `process_criteria` документа версии | оценки разных версий набора не сравниваются |
| профиль оценки из перечисления, статус «процесса» из перечисления | сортировки и сравнение |
| **нет поля с общим итогом двух оценок** | FR-RS-04 |
| нет ключа `emotion` на любой глубине | FR-RS-02 |
| у прерванной сервером сессии оценок нет | ограничение базы `sessions_abandoned_no_grade` |

Проверки, которые **не** делаются: пересчёт чисел, сверка эпизодов с логом ходов, проверка цитат.
Если клиент пришлёт согласованный по форме, но неверный по смыслу результат, портал его примет.
Это осознанная граница (раздел 12).

### 8.3. Куда что ложится

| Приходит | Ложится в |
|---|---|
| финал и его название | `sessions.final_id`, `final_title` |
| буква | `sessions.result_rank` |
| число «результата» и максимум | `sessions.result_number`, `result_max` |
| статус и число «процесса» | `sessions.process_status`, `process_number` |
| полосы шести критериев | `sessions.criteria_bands` (jsonb) |
| профиль оценки, отметка «повезло» | `sessions.scoring_profile`, `lucky` |
| блок оценок целиком, **без цитат** | `sessions.scores` (jsonb); эпизоды в нём указывают на номер реплики |
| ответ судьи после разговора **как пришёл** | `sessions.judge_answer_enc` — шифр ключом участника |
| число запросов к судье | `sessions.judge_attempts` |

Цитаты живут только в шифрованном ответе судьи и в шифрованных текстах реплик; в открытом
`scores` их нет, поэтому после уничтожения ключа участника блок оценок остаётся читаемым
и обезличенным.

### 8.4. Повторный запрос к судье

Если судья участника не ответил, «процесс» получает статус `not_received`. Повторный запрос
делает **клиент**, а не портал: он берёт у портала данные для запроса (транскрипт, решения судьи
по репликам, журнал предложений, интересы оппонента, тексты раскрытых фактов) и присылает
полученный ответ. Сохранённый и проверенный ответ больше не перезапрашивается — повторная
присылка получает 409.

## 9. Безопасность и приватность

### 9.1. Ключи и шифрование

Весь модуль — две функции «зашифровать» и «расшифровать» плюс обёртка ключей.

```
ARENA_MASTER_KEY (32 байта, переменная окружения, в базу не попадает)
   ├── шифрует ключ данных каждого участника → subjects.data_key_wrapped
   │      └── ключом участника (AES-256-GCM, случайный nonce перед шифром) шифруются:
   │            turns.text_enc
   │            turns.opponent_judge_comment_enc
   │            sessions.judge_answer_enc
   │            objections.text_enc, objections.response_enc
   │            consent_records.shown_text_hmac (именно HMAC на ключе участника)
   └── шифрует напрямую ключи провайдеров:
          trainer_profiles.openrouter_key_enc
          trainer_profiles.model_server_token_enc

ARENA_CODE_HMAC_SECRET → HMAC кодов доступа (полный код и селектор),
                          токенов участника и ссылок на репетицию
```

Почему у согласия HMAC, а не простой хеш: шаблон текста известен, и перебор по списку сотрудников
восстановил бы человека за обезличенным номером.

Демо-сессии пишутся на одного демо-участника со своим ключом — поэтому код обработки сессий
одинаков для демо и не демо, а гостей друг от друга отличает номер гостя из токена.

### 9.2. Ключи провайдеров наружу

- В портал ключ **не возвращается никому**, даже администратору: он видит только последние
  4 символа. Ответы не-администраторам строятся из представления `trainer_profiles_public`,
  где нет ни ключей, ни последних символов (FR-PF-04).
- Целиком ключ получает только клиент-тренажёр, и только в двух местах: при старте сессии
  и при погашении ссылки на репетицию.
- **Ключ OpenRouter кладётся в ответ только при согласии на внешнюю нейросеть** (FR-AC-07,
  NFR-S-01). Нет согласия — в настройках нет ни адреса, ни ключа OpenRouter; нет и нашего
  сервера в профиле — старт отвечает 409.
- **Гостю демо ключи не выдаются вовсе**: разговор идёт на заглушке. Исключение — переменная
  окружения `DEMO_MODEL_KEYS=1`, которую включают только на стенде жюри. Иначе любой в интернете
  проходит демо-вход и уносит ключи.
- Ключ, оказавшийся на компьютере участника, можно оттуда достать. Поэтому **лимит расходов
  на самом ключе провайдера обязателен** (NFR-C-01), а при утечке ключ меняется в профиле
  и доходит до клиентов при следующем старте.

### 9.3. Отзыв согласия

Одна транзакция, ровно в этом порядке:

```sql
BEGIN;
  UPDATE assignments  SET cancelled_at = now(), cancel_reason = 'consent_withdrawn' …
  UPDATE access_codes SET revoked_at   = now(), revoke_reason = 'consent_withdrawn' …
  DELETE FROM people  WHERE subject_id = $subject;
  UPDATE subjects     SET data_key_wrapped = NULL, key_destroyed_at = now() …
  INSERT INTO audit_log (…, action = 'consent_withdrawn', subject_id = $subject, …);
COMMIT;
```

После неё имени нет нигде, а журнал, лог ходов, сессии, согласия и решения остаются на месте
под обезличенным номером. Идущая сессия доигрывает, но портал уже не может зашифровать её новые
реплики и пишет их без текста — решения судей, шкалы и предложения сохраняются обезличенными.

**Следствие для кода:** после уничтожения ключа сессию нельзя расшифровать, а значит, нельзя
и показать её транскрипт. Все пути чтения текстов обязаны корректно работать с отсутствующим
ключом — показывать «текст удалён по отзыву согласия», а не падать.

### 9.4. Вход и токены

| Что | Как |
|---|---|
| Вход в портал | логин и пароль (argon2id) → cookie `arena_session`: httpOnly, Secure, SameSite=Strict, 8 часов без действий |
| Защита от чужих сайтов | SameSite=Strict плюс правило «изменяющие запросы принимают только `application/json`»; **исключение — два адреса авторства голосом**, где принимается `multipart/form-data` с одним файлом mp3 |
| Токен участника | подписанный HMAC, несёт назначение, номер участника и срок 12 часов; хранится в `sessionStorage` вкладки |
| Токен гостя демо | то же плюс `demo_guest_id`, по которому гость видит только свои сессии |
| Токен репетиции | привязан к одной репетиции и к пользователю, получившему ссылку; годится только для загрузки записи |
| Проверка прав | **всегда по базе, на каждом запросе** — ни роль, ни доступ к группам, ни статус назначения в токене не хранятся |

Отменили назначение или перевыпустили код — токен больше не начинает новых сессий и не выдаёт
настройки, но **идущая сессия доигрывается**: её события, завершение и повторный запрос к судье
принимаются.

### 9.5. Коды доступа

Формат `ARENA-XXXX-XXXX-XXX`: десять случайных символов Crockford Base32 (50 бит) и контрольный.
В базе только два HMAC: от всего кода и от первых четырёх символов (селектор).

```
ввод кода → найти действующий код по selector_hash
          → сравнить code_hash
          ├── совпало  → вход
          └── не совпало → failed_attempts + 1
                         → на пороге из настроек → blocked_at (навсегда)
```

Без селектора неудачные попытки не с чем связать и блокировать нечего. Подбирающий должен
сначала попасть в чей-то селектор (20 бит), а потом у него десять попыток на оставшиеся
30 бит: вероятность угадать один код — не больше 10 из 2³⁰. Ограничение частоты по адресу
держит приложение, блокировку снимает только администратор.

### 9.6. Чего нет

Кадров с камеры, точек лица, метки эмоции, звука, кода доступа в открытом виде, ключей
в открытом виде, общего числа из двух оценок. Ни в API, ни в базе, ни в логах.

## 10. Отпечаток, авторство сценария и оставшаяся заглушка

### 10.1. Отпечаток документа

```go
// internal/modules/scenariodoc
type Fingerprinter interface {
    Fingerprint(document []byte) (string, error) // 64 шестнадцатеричных знака
}
```

**SHA-256 от канонической записи JSON** — ключи по порядку, без пробелов, UTF-8 — с удалением
`passport.version`, `passport.tags`, `passport.origin` и `authoring` перед подсчётом. Делается
сразу, заглушки здесь нет.

Удаление `passport.version` обязательно: номер версии лежит внутри самого документа, и без
этого отпечаток черновика никогда не совпал бы с отпечатком опубликованной версии, а ответ
409 `nothing_changed` при публикации без изменений не сработал бы. Остальные три убираются,
чтобы экспорт и повторный импорт давали тот же отпечаток (приёмка FR-SC-14).

**Роль у отпечатка ровно одна — опознать версию документа.** По нему различаются версии
(`scenario_versions.fingerprint`, уникален внутри сценария), по нему же портал видит, что
черновик не изменился с прошлой публикации, и автор может пройтись по версиям своего сценария.
Ничего другого отпечаток не решает: допуск к режиму «оценка» по числу репетиций ровно
на отпечатке (FR-SC-11) снят, см. раздел 12.5.

### 10.2. Авторство сценария голосом и текстом

Методолог описывает сценарий голосом; клиент портала собирает речь в mp3 и отправляет файл
на бэкенд. Портал расшифровывает запись и отдаёт описание модели, которая возвращает документ
сценария целиком — с условиями переходов, пределами сделки и скрытыми фактами. Готовый
документ уходит на фронтенд портала и показывается интерактивной формой.

Способов шесть, и они равноправны:

| Способ | Адрес |
|---|---|
| создать голосом | `POST /api/portal/scenarios/{scenarioId}/generation/audio` |
| создать текстом | `POST /api/portal/scenarios/{scenarioId}/generation/text` |
| править голосом | `POST /api/portal/scenarios/{scenarioId}/draft/voice-edit` |
| править текстом | `POST /api/portal/scenarios/{scenarioId}/draft/text-edit` |
| создать формой | `POST /api/portal/scenarios` с `origin = manual` — готовый каркас (FR-SC-02) |
| править формой | `PUT /api/portal/scenarios/{scenarioId}/draft` |

Ход задания читается с `GET /api/portal/scenarios/{scenarioId}/generation`; экран опрашивает
его раз в две секунды.

```go
// internal/platform/ai
type Transcriber interface {
    Transcribe(ctx context.Context, audio io.Reader) (string, error)
}
type ScenarioGenerator interface {
    Generate(ctx context.Context, brief string, base []byte, problems []string) ([]byte, error)
}
```

**Задание идёт тремя этапами:** `transcribing` (пропускается у текстового ввода) →
`generating` → `checking`. На проверке работает `scenariodoc`: схема и пятнадцать правил.
Ошибки возвращаются модели текстом, **не больше двух повторов**, дальше правит человек
в форме. При правке готового черновика модель получает текущий документ и указание, что
изменить, и возвращает документ целиком — проверка та же.

**mp3 не хранится нигде:** ни столбца в базе, ни файла на диске, ни байта в логе. Файл живёт
в памяти процесса на время расшифровки. Сохраняется только расшифровка — в
`scenarios.generation`; в `audit_log.details` она не попадает.

Состояние задания хранится в `scenarios.generation`
(`{input_kind, status, stage, transcript, instruction, attempts, check, error, started_at}`),
само задание живёт в памяти процесса, поэтому **при старте портал переводит оставшиеся
`running` в `failed`** с текстом «Портал перезапускался — повторите»: иначе генерация навсегда
осталась бы в состоянии «идёт».

**Откуда модель и ключ — решено:** отдельные переменные окружения портала (раздел 11.2),
а не расширение закрытой схемы настроек профиля тренажёра. Профиль описывает разговор,
а генерация к разговору отношения не имеет. Переменные **необязательные**: без них портал
поднимается как обычно, четыре адреса авторства отвечают 503 с русским текстом «Модель
генерации не настроена», а форма, шаблоны, копия и импорт работают. Так держатся NFR-D-01,
NFR-D-02 и NFR-D-03: ни сборка, ни первый запуск, ни демо-данные модели не требуют.

`scenarios.origin` у голоса и у текста одинаковый — `brief`; чем именно задавали, видно
в `generation->'input_kind'`. Схема базы под всё это не меняется.

### 10.3. Проверка профиля тренажёра — единственная оставшаяся заглушка

```go
type ProfileChecker interface {
    Check(ctx context.Context, p ProfileWithKeys) ([]CheckLine, error) // по строке на проверку
}
```

**Сейчас:** заглушка возвращает четыре строки со статусом «не проверялось». **Целевая:** короткий
тестовый запрос к трём моделям и к синтезу речи, с ответом, временем и текстом ошибки по каждой
(FR-PF-06, SHOULD). Ограничение времени — 20 секунд, это единственный адрес портала, которому
разрешено столько ждать.

### 10.4. Что заглушкой не закрывается

Проверка сценария, шаблоны, каркас «вручную», каталог узлов условий, применение уровня
сложности и отпечаток — **не заглушки**: без них не работают публикация версий и половина
экранов редактора. Это обычный код модуля `scenariodoc`, и он пишется целиком.

## 11. Развёртывание

### 11.1. Состав

```
docker-compose.yml
  postgres   PostgreSQL 16, том с данными, healthcheck
  portal     один бинарь Go, зависит от healthcheck postgres
```

Порядок первого запуска: контейнер Postgres поднимается → роль-владелец выполняет
`db/schema/arena-db.sql` → портал стартует под `arena_app`, видит пустую базу (нет ни одного
пользователя) и заливает демо-данные → печатает в лог режим работы и адрес.

**Приёмка NFR-D-01:** клон и одна команда, меньше десяти минут на чистой машине с каналом
50 Мбит/с, бюджет около 3,7 ГБ. Ни один хост третьей стороны не участвует в сборке и в первом
запуске (NFR-D-03).

### 11.2. Переменные окружения

| Переменная | Что задаёт | Обязательна |
|---|---|---|
| `ARENA_DATABASE_URL` | подключение под ролью `arena_app` | да |
| `ARENA_MASTER_KEY` | мастер-ключ шифрования, 32 байта | да |
| `ARENA_CODE_HMAC_SECRET` | секрет HMAC кодов, токенов и ссылок | да |
| `ARENA_LISTEN` | адрес и порт HTTP | нет, по умолчанию `:8080` |
| `ARENA_STT_URL`, `ARENA_STT_KEY`, `ARENA_STT_MODEL` | распознавание речи для авторства голосом | нет; без них адреса авторства отвечают 503 |
| `ARENA_GEN_URL`, `ARENA_GEN_KEY`, `ARENA_GEN_MODEL` | модель, которая собирает документ сценария | нет; без них адреса авторства отвечают 503 |
| `ARENA_DEMO` | демо-режим; выключение — одна переменная (FR-AC-09) | нет, по умолчанию включён |
| `DEMO_MODEL_KEYS` | выдавать ли гостям демо ключи моделей; **только на стенде жюри** | нет, по умолчанию выключено |
| `ARENA_LOG_LEVEL` | уровень лога | нет |

Портал при старте проверяет обязательные переменные и **падает с понятным сообщением**, если
чего-то нет: молча запуститься без мастер-ключа он не имеет права.

**В лог при старте печатается:** версия, включён ли демо-режим, выдаются ли ключи демо-гостям,
настроены ли расшифровка речи и модель генерации, адрес прослушивания, время старта (оно же
участвует в расчёте таймаута брошенных сессий).

### 11.3. Демо-данные (NFR-D-04)

Заливает скрипт приложения, а не SQL: отпечатки сценариев считает тот же код, что и в работе,
поэтому демо-данные не расходятся с настоящими. Сценарии для демо готовы заранее и моделью
не генерируются — первый запуск не обращается наружу (NFR-D-03). Состав: настройки портала, два пользователя
(методолог и администратор), профиль по умолчанию без ключа, группа с открытым методологу
доступом, четыре вымышленных сотрудника и один демо-участник, четыре текста согласий, два
сценария разных типов, три репетиции с загруженной записью, четыре назначения с кодами (код
активного напечатан в README), ответы на согласия, три завершённые сессии с разными финалами
(у одной — нарушение оппонента без отметки «просмотрено»), одно возражение без ответа, записи
в журнале.

**Приёмка:** после первого запуска все экраны портала непустые.

**Зависит от открытого решения 03:** если оценочный контур показываем вживую, второй сценарий
публикуется в режиме «оценка» с тремя репетициями и пометками «ДЕМО, вымышленный сотрудник»,
и экран кадрового решения проходится до конца; если нет — он в режиме тренировки, и экран
решения показывает только отказ «тренировка — не основание для кадрового решения».

### 11.4. Работа без интернета

Без ключа и сети разговор идёт на заглушке — записанном диалоге с размеченными ходами
(NFR-D-02). Это целиком клиентская механика, но портал обязан её не ломать: сессия на заглушке
принимается, помечается `stub_used`, и **обе оценки в ней считаются** и сохраняются как обычно.

## 12. Отклонения от спецификации и риски

Ни одно из этих отклонений не замалчивается: каждое названо, у каждого есть цена и способ
вернуться назад.

### 12.1. Go вместо Node.js

`arena-api.md` (раздел 1) и `arena-db.md` написаны в расчёте на один процесс Node.js, который
подключает тот же пакет движка на TypeScript, что и клиент. Язык изменён на Go.

**Цена:** ни одна функция клиента не переиспользуется — всё, что порталу нужно от документа
сценария, он реализует сам. **Возврата не предполагается.**

### 12.2. Пакет движка не используется

Формат сценария по `arena-scenario-format.md` (раздел 19) принадлежал пакету движка; теперь
он принадлежит порталу. Открытое решение 02 закрыто в пользу портала.

**Цена:** клиент и портал должны одинаково понимать документ, а общего кода у них нет. Согласие
держится на контракте `arena-api.yaml` и на документе формата, а не на общей библиотеке.
Расхождение вылезет не при сборке, а на первой сессии.

**Что делать:** контракт и формат — единственные точки согласования, и менять их можно только
согласованно с командой клиента. Номер формата (`arena-scenario/1`) передаётся клиенту вместе
с документом: клиент, не знающий номера, не должен начинать сессию.

### 12.3. Документ уходит клиенту целиком

FR-AC-04 требовал: до старта сессии клиент получает только публичную часть (легенда, роль
участника, карточка оппонента, его видимые предметы торга), а приватную (пределы оппонента,
тексты скрытых фактов, схема этапов, условия переходов, финалы) — отдельным запросом после
старта, только в память. Деление документа не реализуется.

**Цена:** приватная половина оказывается на компьютере участника **до** старта сессии. Участник
с инструментами разработчика может прочитать пределы оппонента и тексты скрытых фактов —
то есть пройти сценарий, зная ответы. Для внутреннего тестирования это приемлемо, и ровно так
написано в обосновании самого требования; для оценочного использования — нет.

**Что остаётся:** автотест FR-AC-04, который брал адреса из роутера и проверял, что до старта
ни один ответ не содержит пределов оппонента, снимается. Три запроса до первой реплики
(NFR-P-02) сохраняются, но третий больше не выдаёт «приватную половину» — он только создаёт
сессию и выдаёт доступ к моделям.

**Возврат:** деление документа — чистая функция над JSON по списку из раздела 16 формата.
Добавляется в `scenariodoc` и включается в двух местах выдачи, схему базы менять не нужно.

### 12.4. Портал не пересчитывает оценки

`arena-scoring.md` (1.3) требовал: портал, получив запись сессии, пересчитывает обе оценки теми
же функциями той же версии движка и хранит свой расчёт, а при расхождении с расчётом клиента
пишет ошибку в журнал и показывает свой.

**Цена:**
- Приёмка FR-RS-01 «по сохранённой записи балл пересчитывается без обращения к моделям»
  не проходит — пересчитывать нечем.
- Сверки нет: портал показывает то, что прислал клиент. Ошибка в подсчёте на клиенте станет
  видна не сразу.
- Приёмка FR-RS-03 «сто пересчётов из одной записи дают одинаковый результат» проверяется
  на стороне клиента, а не портала.

**Что остаётся:** запись сессии по-прежнему хранит **всё**, из чего оценки считаются — реплики,
решения обоих судей по каждой реплике, шкалы, шаги уступок, переходы, раскрытые факты, журнал
предложений, признак перебитой реплики, сырой ответ судьи после разговора, версию сценария,
уровень, набор критериев и профиль оценки. Схема базы к пересчёту готова.

**Возврат:** добавляется модуль пересчёта, который читает то же самое и пишет свой расчёт рядом.
Схему базы менять не нужно.

### 12.5. Допуск к режиму «оценка» снят

FR-SC-11 требовал: перевод сценария в режим «оценка» разрешён только после N репетиций ровно
на отпечатке публикуемого черновика, N задаёт администратор, по умолчанию 3. Требование снято:
отпечаток опознаёт версию документа и больше ничего не решает.

**Как это ложится на базу.** Схема не меняется. При публикации оценочной версии портал пишет
`admission_required = 0`, а в `admission_rehearsals` — фактическое число засчитанных репетиций
на этом отпечатке. Ограничение `scenario_versions_admission` при этом выполняется, публикация
не блокируется. Столбцы и частичный индекс `rehearsals_admission_idx` остаются и питают
справочную строку «k репетиций на этой версии» на экране сценария.

**Цена:** оценочную версию можно опубликовать, ни разу её не отрепетировав. Репетиция
остаётся тем, чем была, — прогоном автора перед публикацией (FR-SC-10).

**Возврат:** `admission_required` заполняется из `portal_settings.admission_rehearsals`,
и публикация отклоняется при недоборе. Одно условие в службе публикации, схема базы к этому
готова.

### 12.6. Анкета и три шага генерации отменены

FR-SC-03 требовал анкету из десяти полей, FR-SC-04 — генерацию в три шага с подтверждением
каждого человеком. Оба заменены одним проходом: свободное описание голосом или текстом сразу
превращается в полный документ (раздел 10.2).

**Цена:** приёмка FR-SC-04 «повторная генерация шага 3 не затирает правки шагов 1 и 2»
проверять больше нечего — шагов нет. Человек по-прежнему видит и правит результат, но уже
в форме, а не между шагами. Если модель ошиблась в числах, правка идёт в форме или голосовым
указанием, а не перезапуском одного шага.

**Возврат не предполагается:** голосовой путь — продуктовое решение заказчика, а не упрощение.

### 12.7. Сводка

| Требование | Состояние | Возврат |
|---|---|---|
| FR-AC-04 приватная половина после старта | **не выполняется** | функция деления в `scenariodoc`, схема базы не меняется |
| FR-RS-01 пересчёт по записи без моделей | **не выполняется** (хранение — да, пересчёт — нет) | модуль пересчёта, схема базы не меняется |
| FR-SC-09, FR-SC-14 отпечаток | выполняются | — |
| FR-SC-11 допуск к оценке по репетициям | **снято** (12.5) | одно условие при публикации |
| FR-SC-03, FR-SC-04 анкета и три шага | **отменены**, заменены авторством голосом и текстом | не предполагается |
| FR-PF-06 проверка профиля | не выполняется | реализация интерфейса |
| FR-RS-03 воспроизводимость пересчёта | проверяется на клиенте | вместе с 12.4 |

## 14. Порядок реализации

Двое разработчиков. Фазы подобраны так, чтобы после каждой было что показать и чтобы двое
не мешали друг другу: в каждой фазе две дорожки.

| Фаза | Дорожка A | Дорожка B | Что работает в конце |
|---|---|---|---|
| **1. Каркас** | `cmd/portal`, `platform/config`, `platform/pg`, `platform/httpx`, `platform/log`, линтер границ, Docker Compose, выполнение `arena-db.sql` | `platform/crypto` (мастер-ключ, ключи участников, HMAC, argon2id), `audit`, `settings` | процесс поднимается, база создаётся, журнал пишется, ошибки — в `problem+json` |
| **2. Вход и люди** | `auth`: вход по cookie, роли, доступ к группам, пользователи | `people`: сотрудники, группы, номера, перевод, отзыв согласия | в портал можно войти, права работают, сотрудники заведены |
| **3. Сценарии** | `scenariodoc`: схема документа, пятнадцать правил, уровни сложности, каталог узлов, шаблоны, каркас, отпечаток | `scenarios`: черновик, проверка при сохранении, публикация версий, библиотека, импорт и экспорт, архив | методолог создаёт сценарий формой и публикует версию |
| **3а. Авторство голосом** | `platform/ai`: расшифровка речи и генерация документа | `generation`: приём mp3 и текста, задание в три этапа, два повтора при ошибках проверки, правка черновика по указанию | сценарий надиктовывается голосом и правится голосом или в форме |
| **4. Выдача и сессия** | `profiles`: настройки, ревизии, ключи, профиль по умолчанию | `assignments`: назначения, коды, блокировки, перевыпуск; затем `sessions`: вход по коду, старт, выдача документа и ключей | сотрудник входит по коду и получает всё для разговора |
| **5. Разговор** | `sessions`: приём событий хода, завершение, статусы, поздние события, повторный запрос к судье | `consents`: тексты, варианты, ответы, письменные отметки; `jobs`: закрытие брошенных сессий | сессия проходится от начала до конца и сохраняется целиком |
| **6. Результаты** | `results`: проекции для HR и участника, разбор до цитаты, запись сессии, урезанный вид, отметка «просмотрено» | `analytics`: здоровье сценария, сравнение, аналитика группы, динамика, «мало данных» | HR видит результаты и статистику |
| **7. Право и выгрузки** | `decisions`, `objections` | `exports`: CSV и XLSX, предпросмотр, журналирование | кадровый контур закрыт целиком |
| **8. Демо и остаток** | `demo`: гостевой вход, демо-данные | `rehearsals`; проверка профиля — заглушка | клон и одна команда: все экраны непустые, демо проходится |

**Что делать параллельно с самого начала, а не в конце:**

- Тесты на каждое из пятнадцати правил проверки сценария — по сценарию-нарушителю на правило
  (приёмка FR-SC-08, в исходной спецификации таких нарушителей 28).
- Тест «в схеме API нет поля для эмоций, и запрос с ключом `emotion` отклоняется до записи
  тела в лог» (FR-RS-02).
- Тест «нигде в коде не складываются две оценки» (FR-RS-04).
- Тест «пользователь без доступа к группе получает 403, а не пустой список» — на всех адресах
  результатов (FR-AC-08).
- Таблица NFR-PR-03 и тест, сверяющий её со списком столбцов схемы: он роняет сборку при
  появлении нового столбца без строки в таблице. Заполняется **до первого пилота, не после**.
